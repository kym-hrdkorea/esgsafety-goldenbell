> 이 문서는 `spec/business-rules.md`·`spec/api-contract.md`를 **보충**한다. 충돌 시 이 문서가 우선한다.

## A. 해설 단계 새로고침 — 조건부 허용 (규칙 2 정밀화)

**결정: 새 엔드포인트를 만들지 않는다. `GET /item`에서 응답 단계에 따라 필드를 다르게 준다.**

규칙 2의 목적은 "답하기 전에 정답이 새는 것"을 막는 것이다. 이미 답한 문항은 사용자가 정답을 알고 있으므로 반환해도 문제가 없다. 판정 기준은 **서버의 `answered_at`** 이며 클라이언트가 보낸 phase 값을 신뢰하지 않는다.

| 조건 | `answer`·`explanation`·`legalRef` |
|---|---|
| `answered_at IS NULL` (answering) | **금지** |
| `answered_at IS NOT NULL` 또는 `is_timeout` (explained) | **허용** |

**단, 아래 3개는 단계와 무관하게 모든 응답에서 영구 금지한다.**
`measureCode` / `anchorCode` / `level`
→ 이건 정답 유출이 아니라 **성과측정 무결성** 문제다. 참가자가 측정 문항을 식별하면
`v_matched_pre_post`(캠페인 핵심 성과지표)가 오염되고, 오염 사실이 화면에 드러나지 않는다.

두 금지 규칙의 근거가 다르므로 범위도 다르다. 혼동하지 말 것.

## B. 내 순위 표시 — 본인 순위 1건에 대해 뷰 조회 허용

**결정: 순위 목록은 `ranking_snapshot`만 읽는다. 본인·본인 부서 순위 1건은 뷰 직접 조회를 허용한다.**

원래 규칙의 목적은 "요청마다 전체 순위 집계가 도는 것"을 막는 것이었다. 그 근거는 목요일 1일 개방 기준 피크 38 req/s였는데, **월~금 5일 개방으로 변경되면서 실측 피크가 1 req/s 미만**으로 떨어졌다. 본인 순위 1건 계산은 이 부하에서 문제가 되지 않는다.

- `GET /api/dashboard`의 `me.averageRank` / `me.departmentRank` → `v_rank_average` / `v_rank_department`에서 본인 행만 조회 (Q항 개정 — 원래 `me.totalRank`/`v_rank_total`)
- `GET /rounds/[no]/result`의 `roundRank` → `v_rank_round`에서 본인 행만 조회
- 순위 목록 3종(`round`/`average`/`department`)은 **여전히 snapshot만** 읽는다 (Q항 개정 — 원래 `total` 포함 4종)
- 본인이 최소 회차 미달이면 `averageRank: null`, `rankEligible: false`로 반환하고
  화면에는 `3회 이상 참여하면 순위에 반영됩니다`를 표시한다

`ranking_snapshot.payload`에 전체 순위를 담는 방식은 쓰지 않는다. 불필요하게 복잡하다.

## C. 최소 회차 값의 단일 출처 — `fn_min_rounds()`

**결정: API와 화면은 항상 `fn_min_rounds()` 반환값을 쓴다. `app_config.min_rounds_for_ranking`을 직접 읽지 않는다.**

`app_config`의 값은 그 함수의 **입력 파라미터**일 뿐이다. 직접 읽으면 캠페인 1·2주차에
"순위표는 전원 포함인데 안내 문구는 3회 이상 필요"라는 모순이 화면에 노출된다.

`fn_min_rounds()`의 회차 수는 이미 열렸거나 공개된 회차가 아니라 `closes_at < now()`인
**실제 종료 회차**를 센다. 3회차 개방 순간에 임계값이 0에서 3으로 뛰어 순위표가 비는
전환을 피하고, 3회차가 금요일에 종료된 뒤 다음 집계부터 3회 조건을 적용한다.

- `GET /api/dashboard`의 `minRoundsRequired`는 `fn_min_rounds()` 결과를 담는다
- 이 값이 `0`이면 안내 문구를 **표시하지 않는다**
- `lib/config.ts`는 `min_rounds_for_ranking`을 노출하지 않는다(실수 방지)

## D. 회차 완료 시점 — 12번째 제출 시 즉시 완료

**결정: 마지막 문항의 `POST /answer` 시점에 완료 처리한다.**

`POST /next`는 마지막 문항에서는 상태를 바꾸지 않고 `isCompleted: true`만 반환한다(멱등).

## F. 소속(org_unit) 순위 — 적재하되 미노출 (★ 중요)

**결정: `refresh-rankings`가 `kind='org_unit'`도 적재한다. 대시보드에는 노출하지 않는다.**

이건 단순한 예비 기능이 아니다. **실제로 필요해질 가능성이 높다.**

```
부서 193개 / 직원 1,800명 → 부서 평균 9.3명
참여율 30% 가정 → 부서당 참여자 약 2.8명
부서 순위 임계값 = 3명
```

→ **부서의 절반 가까이가 순위에서 제외될 수 있다.** 부서 순위 탭이 텅 비면 부서 포상의 근거가 사라진다.

**운영 지침**: 1~2회차 실제 데이터로 아래를 확인한 뒤 노출 단위를 최종 결정한다.
```sql
SELECT count(*) FROM v_rank_department;   -- 3명 이상 부서 수
SELECT count(*) FROM v_rank_org_unit;     -- 5명 이상 소속 수
```
부서가 20개 미만이면 소속(50개) 단위로 전환한다. 뷰와 적재가 준비되어 있으므로
탭 라벨과 조회 kind만 바꾸면 된다.

# P2 착수 전 추가 결정 (G항 후속)

## G-1. 관리자 잠금 컬럼 — 추가한다 (수정 완료)

**결정: `admin_user`에 `failed_attempts` / `locked_until` / `last_login_at`을 추가한다. `db/01_schema.sql` 수정 완료.**

"DB 구축 전인 지금이 스키마를 고칠 수 있는 유일한 시점"이라는 판단이 정확하다.
규칙 9-1은 **구축 이후의 스키마 드리프트**를 막기 위한 것이고, 최초 구축 전 정정은 대상이 아니다.

추가하는 이유:
- `participant`와 **완전히 동일한 패턴**이므로 T01의 잠금 로직을 그대로 재사용한다. 구현 비용이 사실상 0
- 지금 빠뜨리면 이후에는 되돌릴 수 없다

**단, 임계값은 참가자보다 완화한다.**

| 대상 | 임계값 | 근거 |
|---|---|---|
| 참가자 | 5회 / 15분 | 4자리 PIN = 조합 1만 개. 무차별 대입이 실제 위협 |
| 관리자 | **10회 / 10분** | 일반 비밀번호라 대입 위험이 낮고, 반대로 **잠금 자체가 운영 위험** |

관리자는 1~2명뿐이다. 캠페인 진행 중 유일한 운영자가 잠기면 그게 더 큰 사고다.
`login_id`를 아는 사람이 반복 실패로 운영자를 상시 차단하는 서비스 거부 시나리오도 있다.

**잠금 시 해제 방법** — Supabase 대시보드에서 직접 실행한다. 별도 관리 화면을 만들지 않는다.
```sql
UPDATE admin_user SET failed_attempts = 0, locked_until = NULL WHERE login_id = '...';
```

`app_config`에 `admin_max_attempts`(10) / `admin_lock_minutes`(10)를 추가했다. 하드코딩 금지 규칙이 그대로 적용된다.

## G-2. 관리자 쿠키 — `path=/` + 이름 분리

**결정: 추천안 1번. `admin_session` 쿠키를 `path=/`로 발급하고, 참가자 쿠키와 **이름만** 분리한다.**

`path=/admin`은 제 과잉 명세였다. 지적이 정확하다 — `/api/admin/**`에 쿠키가 실리지 않아 관리자 API가 전부 401이 된다.

원래 의도는 "참가자 세션과 관리자 세션이 섞이지 않게" 하는 것이었고, **쿠키 이름 분리만으로 그 목적이 완전히 달성된다.** path 스코프는 브라우저 전송 범위만 좁히는 것이라 보안 통제가 아니다. 검증은 어차피 서버가 한다.

| 쿠키 | 이름 | path | 속성 |
|---|---|---|---|
| 참가자 | `hq_session` | `/` | httpOnly, sameSite=lax, secure, 12시간 |
| 관리자 | `hq_admin` | `/` | httpOnly, sameSite=lax, secure, 12시간 |

**필수 조건**: 이름이 다르므로 교차 사용이 구조적으로 불가능하다.
참가자 엔드포인트는 `hq_admin`을 절대 참조하지 않고, 관리자 엔드포인트는 `hq_session`을 참조하지 않는다.
한쪽 쿠키만 있는 상태로 다른 쪽 API를 호출하면 401이 되어야 한다.

`/admin/api/**`로 라우트를 옮기는 3번 안은 채택하지 않는다. `CLAUDE.md`의
"모든 서버 로직은 `app/api/**`" 디렉터리 규약과 `api-contract.md` 경로를 함께 고쳐야 해서 파급이 크다.

## G-3. 규칙 본문 정정 — 9개 파일 수정 완료

**결정: 추천안 1번. 다만 지적된 2개 파일이 아니라 총 9곳을 고쳤다.**

addendum은 **명시적으로 읽으라고 지시해야만** 읽힌다. "addendum 우선"은 모든 미래의 독자가
addendum의 존재를 알고 반드시 읽는다는 전제에 의존하는 취약한 관례다.

> **원칙: 규칙은 독자가 실제로 보는 곳에 있어야 한다.**

## N. 시간 차등 포인트 도입 — 순위·포상 전용 (2026-07-30, T02 완료 후)

**결정: 순위·포상 산정을 정답 수(score)에서 시간 차등 포인트로 전환한다.
5.2의 "소요시간 정렬 절대 금지"는 "세션 총 소요시간 금지"로 정밀화한다.**

배경: 전 직원 약 1,800명 참여 규모에서 만점자가 다수 나올 것으로 예상된다.
정답 수만으로는 변별이 안 되고 공동 1위가 대량 발생해 포상 근거가 무너진다.

공식(`business-rules.md` 5.0이 본문):
```
문항 포인트 = 정답:        point_base + ROUND(point_time_bonus_max × 남은시간 / 제한시간)
              오답·시간초과: 0
남은시간 = GREATEST(제한시간ms - elapsed_ms, 0)
```
- 기본값 `point_base=100`, `point_time_bonus_max=100` → 문항당 100~200P, 회차 만점 2,400P
- `app_config` 키 2개 신설(`point_base`, `point_time_bonus_max`) — **T03 구현 시 INSERT(DML, 허용 범위)**

**원래 결정(5.2 소요시간 금지)을 뒤집는 근거:**
- 원래 우려는 "속도 경쟁 → 해설 건너뛰기"였다. 포인트의 시간 요소는
  **문항별 답변 시간(served_at→answered_at, 45초 이내)만** 쓴다.
  해설 단계는 시간 무제한이고 다음 문항 타이머는 서빙 시점에 새로 시작하므로,
  해설을 아무리 오래 읽어도 구조적으로 불이익이 없다. 원래 취지(학습 효과 보호)는 유지된다.
- 금지 규칙은 "**세션 총 소요시간·해설 열람 시간을 어떤 점수·순위에도 쓰지 않는다**"로 존속한다.
  P5 감사 11번도 이 기준으로 교체했다.

**적용 범위(사용자 확정):** 대시보드 순위 4종 + 포상만 포인트 기준.
`score`(정답 수)는 결과 화면(`{score} / 12`)·내 기록·복습·성과분석(v_matched_pre_post 등)의
기준으로 유지한다. 성과측정은 정답 여부 기반이므로 포인트의 영향을 받지 않는다.

**구현 지침:**
- 포인트는 **저장하지 않는다.** 이미 전 답변에 기록되는 `elapsed_ms`·`is_correct`에서
  집계 시점에 계산하는 파생값이다. **스키마 변경 불필요**(규칙 6·9-1 유지).
- 단 `db/05_views.sql`의 순위 뷰(v_rank_total/round/average/department + 기초 v_round_score)는
  score 기준이므로 포인트 기준으로 교체해야 한다. **뷰 교체는 DDL이다 —
  T05 착수 전에 교체 SQL을 제시하고 명시적 허가(규칙 9-1 절차) 아래 1회 실행한다.**
  (T05의 `roundRank`가 v_rank_round를 읽으므로 마감은 T09가 아니라 T05 전이다)
- 타이머·채점 파이프라인(T02~T04)은 변경 없음. `elapsed_ms`가 포인트의 원천이 되므로
  D 시나리오(타이머) 정확성의 중요도가 더 올라갔다.
- 화면 반영: 정답 배너 `+{points} SCORE`(T03), 결과 화면 `획득 포인트 {points}P` 병기(T05),

## O. 비밀번호 자율 재설정 도입 (2026-08-04, 개시 전)

**결정: `business-rules.md` 1.1의 "PIN 재설정 기능은 만들지 않고, 관리자 수동 초기화로
처리한다"를 뒤집는다. 사번+닉네임+부서 검증 기반 자율 재설정을 제공한다.**
`functional-spec.md` 2절의 "비밀번호 찾기" 금지 항목도 함께 삭제했다.

배경: 복구 경로가 전혀 없어 4자리 PIN을 잊으면 계정이 영구히 잠긴다. 1,800명 규모
6주 캠페인에서 이 문의가 운영 부담이 되고, 재응시 불가 규칙 때문에 잠긴 사용자는
해당 회차를 그대로 잃는다.

**"조회"가 아니라 "재설정"인 이유:** `password_hash`는 bcrypt cost 10 단방향 해시라
서버조차 원래 PIN을 복원할 수 없다. 조회는 기술적으로 불가능하다.

### 기각한 대안
- **관리자 수동 초기화(기존 규칙)** — 가장 안전하지만 사용자가 직접 해결할 수 없다.
  관리자 화면은 읽기 전용이라 UI 추가도 별도 결정이 필요하다.
- **복구 코드 발급** — 안전하고 진짜 셀프서비스지만 `participant`에 컬럼 추가(DDL)가
  필요하고, 코드를 분실한 사용자는 결국 관리자 경로가 또 필요하다.

### 감수한 위험 — 이 기능을 고치기 전에 반드시 읽을 것
수집 항목이 사번·닉네임·소속·부서뿐이라 본인 확인 채널(이메일·연락처)이 없다.
아래는 스키마 변경 없이 제거할 수 없는 위험이며, 사용자가 인지하고 선택했다.

- **R1.** 사번·닉네임·부서를 아는 사람은 누구나 해당 계정의 비밀번호를 바꿀 수 있다.
  닉네임은 순위표에 공개되고 부서는 소속 공개로 후보가 좁혀지므로(대부분 소속은 부서
  5개 이하) **실질적인 비밀은 사번 하나**다.
- **R2.** 공격자는 한 번만 성공하면 된다. 재설정 후 얻은 12시간 세션은 서버에 저장소가
  없어 취소할 수 없고, 피해자가 비밀번호를 되돌려도 그 세션은 살아 있다. 유일한 축출
  수단은 `SESSION_SECRET` 교체이며 전 직원·관리자 세션을 동시에 무효화한다.
- **R3.** 재설정 성공 시 실제 사용자는 자기 계정에서 잠긴다. 재응시 불가 + 금 23:59
  마감 때문에 마감 직전 공격은 해당 회차 참여를 **영구히** 박탈한다.
- **R4.** 진행 중(`in_progress`) 세션이 있는 계정을 탈취하면 남은 문항을 대신 풀 수 있고,
  재응시 불가이므로 점수가 그대로 확정된다.
- **R5.** 재설정은 감사 기록을 남기지 않는다(신규 테이블 금지). 흔적은 함수 로그의
  참가자 UUID 한 줄과 429 발생량뿐이며 로그 보존 기간이 지나면 사라진다.
- **R6.** 요청 제한은 함수 인스턴스 메모리 기반이라 인스턴스 수만큼 상한이 곱해지고
  콜드 스타트마다 초기화된다. `x-real-ip`는 위조 가능해 IP 단위 제한은 최선노력이다.
- **R7.** 재설정 실패는 계정 잠금 카운터를 올리지 않는다. 특정 계정을 표적으로 한
  부서 추측은 전역 요청 제한에만 의존한다.
- **R8.** 새 비밀번호에 취약 PIN 정책(`0000`·`1234`)을 적용하지 않는다(가입과 동일).
- **R9.** 계정당 재설정 횟수 상한이 없다(카운터 컬럼 없음).

### 운영 런북 — R3 발생 시 PIN 수동 초기화
관리자 화면은 읽기 전용이므로 피해 복구는 수동이다. bcrypt 해시는 Supabase SQL
편집기에서 만들 수 없으므로(`gen_salt('bf')` 필요, `pgcrypto` 가용성 미확인)
로컬에서 해시를 만들어 리터럴로 UPDATE한다.

```bash
node -e "console.log(require('bcryptjs').hashSync('1234', 10))"
```
```sql
UPDATE participant
   SET password_hash = '<위에서 얻은 해시>', failed_attempts = 0, locked_until = NULL
 WHERE emp_no = '<사번>';
```
계정 탈취가 확인된 경우 세션까지 끊어야 하며, 그 수단은 `SESSION_SECRET` 교체뿐이다(R2).

### 함께 수정한 기존 버그
`app/api/auth/login/route.ts`가 미가입 사번에 대해 `bcrypt.compare` **전에** 401을
반환해, 빠른 401 = "미가입 사번" / 느린 401 = "가입됨, PIN 오류"로 갈렸다. 즉 로그인
자체가 타이밍 기반 사번 존재 오라클이었다. `!p` 분기에 더미 해시 대조 1회를 추가했다.
더미 해시는 **유효한 cost-10 해시여야 한다** — 형식이 깨진 문자열은 `compare`가 연산
없이 0ms에 false를 반환해 패딩 효과가 사라진다(실측 183ms vs 0ms).

### 남긴 후속 과제
- `POST /api/auth/signup`의 `409 EMP_NO_TAKEN` / `NICKNAME_TAKEN` 구분은 타인 사번의
  가입 여부를 알려주는 열거 오라클이다. `copy.md` 확정 문안 2개를 통합해야 해서 별도 카드로 넘겼다.
- 누구나 동료 사번으로 먼저 가입해 계정을 영구 점유할 수 있다(이메일 인증 부재의
  구조적 결과, `emp_no`는 UNIQUE이고 삭제 경로가 없다). 개시 전 검토 권장.
- `signup`의 `empNo`에 길이 상한이 없다(재설정에는 `.max(20)` 적용).

`functional-spec.md`(2절), `api-contract.md`(reset-pin 계약), `design/copy.md`(로그인
링크·비밀번호 재설정 섹션), `tasks/tasks.md`(T13).

## P. 휴대폰 수집·비밀번호 자동 설정 (2026-08-20 확정)

**결정**: 회원가입에서 비밀번호(4자리 PIN) 직접 입력을 없앤다. 대신 **휴대폰 번호를
입력받아 `participant.phone`(숫자만)에 저장**하고, **비밀번호는 서버가 휴대폰 끝
4자리로 자동 설정**한다(bcrypt 해시). 로그인 흐름은 사번+4자리 그대로다.

**배경**: 포상 지급 시 수상자 연락 수단이 필요하다. 기존 수집 항목(사번·닉네임·소속·
부서)에는 연락 채널이 없어 decisions #3(연락처 미수집)을 개정했다. 휴대폰은 포상
연락 외 용도로 쓰지 않으며, CSV(`scores`)에만 싣고 관리자 화면 API에는 노출하지
않는다(사번과 동일 원칙). 로그 금지도 사번과 동일하게 적용한다(규칙 10 개정).

**재설정(reset-pin)도 휴대폰 재입력 방식으로 전환**: 사번+닉네임+부서 확인은 그대로,
2단계에서 새 비밀번호 대신 휴대폰 번호를 재입력받아 끝 4자리로 재설정하고
`phone`도 함께 갱신한다. "비밀번호 = 현재 휴대폰 끝 4자리" 불변식이 전 경로에서
유지되고, 번호 변경 시 연락처 갱신 경로를 겸한다.

**검증 규칙**: 하이픈·공백 허용 입력 → `\D` 제거 정규화 → `^01[016789]\d{7,8}$`
(10~11자리). 클라이언트·서버(zod transform→pipe) 동일 규칙. 휴대폰 UNIQUE 제약 없음
(신원 키는 emp_no. UNIQUE 409는 "이 번호로 누가 가입했는지" 열거 오라클이 되고
법인폰 공용 등 정당 사례를 막는다).

**감수한 위험** (O항 위험 목록에 추가):
- **R10.** 비밀번호가 "본인이 고른 비밀값" → "휴대폰 끝 4자리(동료가 알 수 있는
  준공개 정보)"로 바뀐다. 사번+휴대폰을 아는 동료는 로그인이 가능하다. 로그인 잠금
  (5회/15분)이 무차별 대입은 막지만 아는 값 입력은 막지 못한다 — 운영상 감수.
- **R11.** R1 공격자(사번·닉네임·부서를 아는 자)가 재설정에 성공하면 비밀번호와
  함께 **포상 연락처까지 공격자 번호로 바뀐다**. 재설정 성공 로그(pid)가 유일한 흔적.
- R8의 취약 PIN 정책 논의는 파생값 체계에서는 적용 불가(끝 4자리가 `0000`인 번호
  소유자를 거부하면 가입 자체가 막힌다).

**2026-08-20 이전 가입 행**은 `phone IS NULL`이며 예전 PIN으로 계속 로그인된다.
개시 전 시점이라 해당 행은 테스트 계정뿐이었고 전량 삭제했다(실DB participant 0행).

수정한 파일: `app/api/auth/signup/route.ts`·`app/(auth)/signup/page.tsx`(휴대폰 필드),
`app/(auth)/login/page.tsx`(안내 문구), `app/api/auth/reset-pin/route.ts`·
`app/(auth)/reset-pin/page.tsx`(휴대폰 재입력), `lib/admin.ts`·
`app/api/admin/export/[kind]/route.ts`(scores CSV 휴대폰 열), `db/01_schema.sql`

`design/copy.md`·`spec/api-contract.md`·`decisions.md`·`CLAUDE.md` 규칙 10.

## Q. 포상 기준 반영 — 대시보드 3종 재편·부서 종합점수 (2026-08-25 확정)

**결정**: 운영 계획서(ESG안전센터)의 우수자 선정 기준에 맞춰 ① 대시보드 탭을 포상
카테고리와 1:1인 3종(`주간 우수자`=회차별 / `전체 우수자`=평균 / `우수 부서`=부서)으로
재편하고 '전체 누적' 탭을 제거한다. ② 부서 순위 지표를 평균 포인트 단독에서
**종합점수 = (평균 포인트 ÷ 회차 만점 × 100) × 0.5 + (평균 참여율 × 100) × 0.5**로
바꾼다. ③ 홈·대시보드의 '내 순위'는 평균 포인트 기준(`v_rank_average`)으로 전환한다
(`totalRank` → `averageRank` 개명).

**참여율 부활 근거**: decisions #17이 참여율을 폐기한 사유는 분모(부서 정원) 미수집이었다.
운영자가 분모를 **개방 회차 수**(is_published AND opens_at <= now, `fn_open_rounds()`
단일 출처 — C항과 같은 원칙)로 재정의해 폐기 사유가 해소됐다. 정원 데이터는 여전히
수집하지 않는다.

**확정 파라미터**: 가중치 50:50은 뷰 산식 상수(정책 상수 — app_config로 빼지 않아
런타임 임의 변경을 차단). 회차 만점은 app_config 3키(items_per_round·point_base·
point_time_bonus_max) 유도. `min_participants_for_dept`(3) 유지. 참여율은 100% 클램프.
동점 시 참여자 수 많은 쪽 우선. `v_rank_org_unit`(F항 대안 경로)도 동일 산식 적용 —
대안 경로는 산식이 같아야 대안이다.

**snapshot 정리**: cron의 `total` 적재를 중단하고 잔여 `kind='total'` 행은 신코드 배포 후
1회 DELETE(적재 중단만 하면 round 외 kind는 삭제 경로가 없어 영구 잔류). `v_rank_total`
뷰 자체는 유지(DROP은 불필요한 DDL).
