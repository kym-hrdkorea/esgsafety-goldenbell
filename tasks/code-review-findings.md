## A. 높음 (5)

### A-1. 마감된 회차의 진행 중 세션을 재개할 수 없다 — B4 위반, 응시 점수 손실
`app/api/rounds/[no]/session/route.ts:42-65` · 검증 3/3 · 3개 관점에서 독립 발견

회차 개방 검사가 **기존 세션 조회보다 먼저** 있어서 신규 생성뿐 아니라 재개까지 막는다.

```ts
const state = roundState(round);
if (state !== "open") {
  return apiError(403, "ROUND_NOT_OPEN", state === "locked" ? MSG.notOpen : MSG.closed);
}
// 1인 1회차 1회 — 기존 세션이 있으면 새로 만들지 않는다 (C1·C2)
let existing = await loadSession(pid, no);
```

- `spec/test-scenarios.md` B4는 "금 23:59:59 직전 세션 시작 → 허용(**시작 후 마감 시각은 세션 진행에 영향 없음**)"으로 확정돼 있다.
- 같은 저장소의 `item`/`answer`/`next`는 의도적으로 회차 상태를 검사하지 않아 B4를 지킨다. `review/route.ts:62` 주석도 "마감 직전 시작한 세션(B4)이 아직 진행 중"인 상태를 전제한다. **서버 내부 규칙이 서로 어긋난 상태다.**
- 응시 화면은 마운트마다 `POST /session`을 호출하므로(`quiz/page.tsx:140`) 새로고침·앱 전환 복귀 한 번이면 걸린다.
- **막다른 길까지 생긴다**: 안내대로 홈 → [복습하기] → `GET /review`가 409 IN_PROGRESS → `review/page.tsx:79`가 다시 `/quiz`로 replace → 다시 403. 무한 루프.

**영향**: 매주 금요일 자정 경계에 응시 중이던 사람 전원. 남은 문항을 풀 수 없고 30분 방치 만료 전까지 결과도 못 본다.

**수정**: 상태 게이트를 기존 세션 조회 **뒤로** 옮긴다. `loadSession` → `expireIfIdle` 후 `in_progress`면 회차 상태와 무관하게 재개, `completed`/`expired`면 409, **세션이 없을 때만** `roundState() !== "open"` → 403. 신규 응시 차단은 그대로 유지된다.

### A-2. 로그인 실패 카운터가 read-modify-write라 5회 잠금을 통째로 우회할 수 있다
`app/api/auth/login/route.ts:52-98` · 동일 패턴 `app/api/admin/auth/login/route.ts:79-119` · 검증 3/3

`failed_attempts`를 SELECT로 읽고 → `bcrypt.compare`(cost 10, 수십~수백 ms) → **읽은 값+1**을 그대로 UPDATE한다. 낙관적 가드(`.eq("failed_attempts", …)`)가 없고, Supabase JS에는 트랜잭션도 컬럼 상대 증분도 없다.

```ts
const priorFails = p.locked_until && new Date(p.locked_until).getTime() <= now ? 0 : p.failed_attempts;
const fails = priorFails + 1;
...
.update({ failed_attempts: fails, locked_until: null }).eq("id", p.id);
```

동시 도착한 N개 실패 요청이 전부 같은 값을 읽고 같은 값을 쓴다 → **N번 틀려도 카운터는 1만 오른다.** `middleware.ts`도 없어 별도 레이트리밋이 없다.

**영향**: `business-rules.md:21-23`이 "4자리는 조합이 1만 개뿐이다 … **이 기능은 필수다**"라고 명시한 바로 그 통제가 무력화된다. PIN 전수 대입 → 타인 계정 진입 → 재응시 불가 규칙 때문에 **피해자의 응시 기회가 소진된다.**

**수정**: 낙관적 동시성. UPDATE에 읽은 값을 조건으로 걸고(`.eq("failed_attempts", p.failed_attempts).select("id")`) 갱신 행이 0이면 재조회 후 2~3회 재시도. **DDL 불필요** — 규칙 9-1에 저촉되지 않는다.

### A-3. 부서 순위 '우리 부서' 배지를 부서명 문자열로 판정 — 동명 부서 108개
`app/(main)/dashboard/page.tsx:183` · 연계 `app/api/dashboard/route.ts:115-129` · 검증 3/3

isMe: r.departmentName === me.departmentName,   // ← 부서명만으로 본인 부서 판정

**수정**: `me`에 `departmentId` 추가 + 스냅샷 payload에 `department_id` 적재 → id 비교. 이름 칸을 `{소속} · {부서}`로 렌더(가입 화면이 이미 쓰는 표기). 계약 문서도 함께 개정.

### A-4. 사전·사후 측정 문항 12쌍 중 6쌍의 유형이 달라 캠페인 핵심 KPI가 구조적으로 왜곡된다 **(미검증 — 적대적 검증 미실행)**
`db/04_seed_items.sql` · `db/05_views.sql:237-270`

실DB 실측(시드 파일과 일치, 96문항 md5 확인):

| 사전 | 유형 | → | 사후 | 유형 |
|---|---|---|---|---|
| M01 `1-05` | ORDER L2 | → | M01P `7-04` | MC4 L2 |
| M03 `1-07` | OX L1 | → | M03P `7-06` | MC4 L1 |
| M04 `1-08` | OX L1 | → | M04P `7-07` | MC4 L1 |

나머지 6쌍(M02·M05·M06·M07·M09·M10)은 MC4 → MC4로 정상.

`gain_pp = post_pct - pre_pct`는 사전·사후가 동일 응답형식이라는 전제 위에서만 '지식 향상도'다. OX는 추측 정답률 50%, MC4는 25%, ORDER 4항목은 4.2%다. **지식이 전혀 늘지 않은 참가자도 사전이 사후보다 약 9pp 높게 나온다** — gain_pp에 하향 편향이 구조적으로 들어 있다. 회차 목표 정답률 70~75% 구간에서 9pp는 '향상 없음'으로 결론이 뒤집힐 수 있는 크기다.

**시한**: 개시 후에는 응시가 쌓여 문항을 바꿀 수 없다. **8/10 이전에만 고칠 수 있다.**

**수정**: 사전 6문항의 `item_type`·`choices`·`answer`를 사후와 동일한 MC4로 맞추는 UPDATE(DML, 스키마 변경 불필요). 불가하면 최소한 성과보고를 유형이 같은 6쌍만으로 한정하는 방안을 승인받는다.

### A-5. `is_published`를 켜는 수단이 저장소 어디에도 없다 — 8주간 수동 콘솔 UPDATE 의존 **(미검증)**
`db/03_seed_rounds.sql:40` · 연계 `lib/quiz.ts:51-53`

`roundState`는 `is_published=false`면 `opens_at`과 무관하게 **무조건 locked**다. 저장소 전체에서 `is_published`는 SELECT 2곳에만 쓰인다 — 이걸 `true`로 바꾸는 코드가 없다. 관리자 화면에 회차 개방 상태를 보여주는 화면조차 없다.

**영향**: 매주 월 00:00 수동 SQL 7번이 전부 성공해야 한다. 실패해도 **아무 데서도 드러나지 않는다** — 참가자 홈엔 '아직 열리지 않았습니다'만, 관리자 화면엔 표시 없음, 로그 없음. 참가자 문의가 들어와야 안다.

**수정**: (a) 관리자 화면에 회차 개방 상태 조회 + 전환 컨트롤을 만들거나, (b) 일정만으로 개방을 판정하도록 하고 8회차를 개시 전 일괄 `true`로 UPDATE. 어느 쪽이든 스키마 변경 불필요. 최소한 관리자 화면에 '회차별 개방 상태' 한 줄은 노출해 조용한 실패를 막아야 한다.

### B-1. 순위 갱신 cron이 60초가 아니라 하루 1회 — 카드와 표가 최대 24시간 어긋난다
