## 운영 계획서의 우수자 선정 기준 (2026-08-26, ESG안전센터)
1. 주간 개인 — 매 회차별 고득점자 상위 10명
2. 종합 개인 — 전체 기간 고득점자 상위 15명. 단 최소 3회 이상 참가자만 대상으로 평균 점수 산출
3. 종합 부서 — 평균 점수(50%) + 평균 참여율(50%) 합산해 2곳
   - 평균 점수 = 부서 참가자의 전체 응시점수 합계 ÷ 전체 응시건수
   - 평균 참여율 = 참가자별 참여율 합계 ÷ 부서 참가자 수

## 운영자가 확정해 준 해석 (임의로 바꾸지 마라)
- "점수"는 **포인트**를 뜻한다. 정답 개수가 아니다.
  (포인트 = 정답당 point_base + 남은시간 비례 보너스, 회차 만점 = items_per_round × (base + bonus))
- 부서 참여율의 분모는 **그 시점까지 개방된 회차 수**다. 전체 6회차 고정이 아니다.
  개방 회차 = quiz_round에서 is_published이고 opens_at <= now()인 회차 수.
- 부서 종합점수는 **만점 대비 %로 환산 후 50:50 합산**한다.
  종합점수 = (부서 평균포인트 ÷ 회차만점 × 100) × 0.5 + (부서 평균참여율 × 100) × 0.5  → 0~100점
- 부서 정원 데이터는 쓰지 않는다(수집하지 않음). 정원 대비 제외 조항은 적용 대상이 아니다.
- 부서 최소 참여 인원 3명 조건(app_config.min_participants_for_dept)은 그대로 유지한다.
- 회차 만점·기준값은 하드코딩하지 말고 app_config에서 읽어라(규칙 7).

## 해야 할 일 1 — 대시보드를 포상 3종에 맞춰 재편
현재 대시보드 탭은 4개다: 전체 누적 / 회차별 / 평균 포인트 / 부서.
이것을 **포상 카테고리와 1:1로 맞춰 3개 탭으로 바꾼다.**
  1번 탭 개인 주간 우수자  ← 회차별 순위 (v_rank_round)
  2번 탭 전체 우수자      ← 평균 포인트 순위 (v_rank_average, 최소 3회 조건 적용)
  3번 탭 우수 부서        ← 부서 순위 (아래 산식으로 개편)
**'전체 누적' 탭은 제거한다.** 포상 기준이 평균이므로 누적을 주 순위로 보여주면
참가자가 6주 내내 다른 기준을 보다가 포상 결과에 문의하게 된다.

함께 확인할 것:
- 홈 요약 카드의 '내 순위'가 현재 v_rank_total(누적)을 읽는다(app/api/dashboard/route.ts).
  누적 탭을 없애면 이 카드도 기준이 어긋난다. **평균 순위 기준으로 바꿔라.**
- 순위 목록은 ranking_snapshot에서 읽고 본인 1건만 뷰를 직접 조회한다(addendum B항).
  이 구조는 유지하라. Cron이 적재하는 kind 목록도 정리 대상인지 판단해 보고하라.
- 화면 문안이 바뀌므로 design/copy.md를 먼저 고치고 코드를 맞춰라(규칙 9).

## 해야 할 일 2 — 부서 순위 산식 개편
현재 v_rank_department는 평균 포인트 단독이다(db/05_views.sql). 계획서대로 참여율을 넣어야 한다.
필요한 값:
  부서 평균포인트 = AVG(v_round_score.points)            ← 계획서의 "점수합 ÷ 응시건수"와 동일
  참가자별 참여율 = 그 참가자의 응시 회차 수 ÷ 개방 회차 수
  부서 평균참여율 = AVG(참가자별 참여율)
  종합점수      = (평균포인트 ÷ 회차만점 × 100) × 0.5 + (평균참여율 × 100) × 0.5
정렬은 종합점수 내림차순, 동점 시 참여자 수 많은 쪽 우선. participants >= 3 조건 유지.
화면에도 종합점수·평균참여율이 보이게 하라(무엇으로 순위가 갈렸는지 참가자가 알 수 있어야 한다).

**이 변경은 CREATE OR REPLACE VIEW = DDL이다. 규칙 9-1에 따라 실행 전에 사용자 승인을 받아라.**
db/05_views.sql(원본)을 먼저 고치고, 적용할 SQL을 보여준 뒤 승인을 요청하라.
0으로 나누는 경우(개방 회차 0)를 NULLIF로 막아라.

## 해야 할 일 3 — 6회차 가상 응시 테스트
`db/e2e-drive.mjs`가 이미 있다. 새로 만들지 말고 이걸 써라.
  node --env-file=.env.local db/e2e-drive.mjs plan      계획만 출력(쓰기 없음)
  node --env-file=.env.local db/e2e-drive.mjs run       8명 전원
  node --env-file=.env.local db/e2e-drive.mjs run 1 4   1~4번만 (슬라이스 병렬 실행 가능)
  node --env-file=.env.local db/e2e-drive.mjs cleanup   테스트 대역만 삭제
문항 정답을 DB에서 읽어 표시 위치로 역산하므로 목표 정답 수가 정확히 만들어지고,
서버 판정이 의도와 다르면 즉시 예외로 멈춘다.

참가자 8명 구성(사번 9000000X 대역, 닉네임 가상응시NN):
  전략기획부 4명 — 3명은 6회차 전부, 1명은 3회차만
  예산부   3명 — 6회차 / 5회차 / 2회차   (부서 최소 3명 경계값)
  성과관리부 1명 — 2회차                 (3명 미달 → 부서 순위에서 빠져야 정상)

검증 순서:
1. 서버 기동, /api/health 200 확인. 현재 DB 상태를 먼저 조회해 보고
   (참가자·세션·문항 수, 회차별 개방 상태, fn_min_rounds() 값).
   **기존 참가자 계정은 절대 지우지 마라.**
2. 8명 응시 수행.
3. 회차가 열려 있는 동안(fn_min_rounds()=0) 검증:
   - 회차별 순위가 포인트 내림차순인가, 상위 10명 추출이 가능한가
   - 2회차만 응시한 사람도 아직 전체 우수자 순위에 포함되는가(필터 미작동 상태)
   - 부서 순위에서 성과관리부(1명)가 빠지고 예산부(3명 경계값)는 들어가는가
   - 부서 종합점수·참여율이 직접 계산한 값과 일치하는가(뷰를 믿지 말고 JS로 재계산해 대조)
4. **캠페인 종료 상황을 재현한다.** quiz_round의 closes_at을 과거로 UPDATE해 회차를 닫고
   fn_min_rounds()가 3이 되는지 확인한 뒤, 2회차만 응시한 가상응시07·08이
   전체 우수자 순위에서 빠지는지 검증한다. 참여율 분모(개방 회차 수)도 함께 확인하라.
   ※ DML이다. 실행 전 원래 일정 값을 파일로 백업하고 검증 후 반드시 복구하라.
5. 순위 스냅샷 갱신(로컬 cron 라우트를 CRON_SECRET Bearer로 호출) 후 대시보드 API가
   뷰와 일치하는지 대조. 응답에 사번·휴대폰·participant UUID가 새지 않는지도 확인.
6. 브라우저로 대시보드 3개 탭을 열어 실제 화면을 확인하고 스크린샷으로 보여라.
   ※ 브라우저 페인 스크린샷이 실패하면 Pillow로 검증 시트를 만들어 대신 보여줘도 된다.

## 확정 경위

### 운영 계획서와 대조해 나온 3가지 불일치와 운영자 확정

| # | 쟁점 | 확정 |
|---|---|---|
| 1 | 계획서의 "점수"가 포인트인지 정답 개수인지 | **포인트**. 정답을 많이 맞히면 포인트도 높지만 기준은 포인트 |
| 2 | 부서 참여율의 분모 | **그 시점까지 개방된 회차 수** (전체 6 고정 아님) |
| 3 | 부서 종합점수 합산 | **만점 대비 %로 환산 후 50:50** |
| 4 | 포상은 평균인데 대시보드 첫 탭은 누적 | **탭을 3개로 재편** — 주간 우수자 / 전체 우수자 / 우수 부서 |
| 5 | 부서 정원 | **불필요**. 정원 대비 제외 조항은 적용 안 함 |
| 6 | 운영 일정 | **2026-09-01 개시** 확정 |

### 이미 일치하던 것

회차당 12문항·6회차 72문항, 문항당 45초, 1인 1회차 1회, 유형 혼합(MC4 53·OX 14·ORDER 4·SHORT 1),
난이도 L1 22·L2 39·L3 11, 사번+휴대폰 끝 4자리 로그인, 종합 개인 최소 3회 조건,
부서 평균 점수 산식(점수합 ÷ 응시건수).

### 테스트를 일정 반영보다 먼저 하는 이유

오늘은 2026-08-25다. 계획서 일정(9/1~10/9)을 지금 DB에 넣으면 **6개 회차가 전부 미개방**이 되어
가상 응시 자체가 불가능하다. 현재 DB는 테스트용으로 전 회차가 2026-08-18~09-25로 열려 있으므로
이 상태에서 6회차를 모두 돌린 뒤, 마지막에 실제 일정으로 바꾸는 순서여야 한다.

### 새 창이 놓치기 쉬운 것

- `db/e2e-drive.mjs`는 이번에 만들어 둔 드라이버다. 정답을 DB에서 역산하므로 목표 정답 수가
  정확히 재현되고, 서버 판정이 어긋나면 그 자리에서 멈춘다. 새로 짜면 이 안전장치가 사라진다.
- 최소 3회 조건은 **회차가 닫혀야** 작동한다(`fn_min_rounds()`는 종료 회차가 2개 이하면 0을 반환).
  회차를 열어둔 채로는 이 필터를 검증할 수 없어서, 종료 상황 재현 단계를 따로 뒀다.
- 뷰에 값을 하드코딩하면 조용히 깨진다. 2026-08-25에 `v_matched_pre_post`의 12쌍 하드코딩 때문에
  KPI가 0행이 될 뻔했고, 쌍 수를 `quiz_item`에서 세도록 고쳤다. 부서 산식도 같은 실수를 반복하지 말 것.
